1. USUÁRIOS (USUARIOS)
============================================================

USUARIOS (
    id (PK),
    nome,
    email (UNIQUE),
    senha,
    perfil,
    id_condominio (FK),
    id_bloco (FK),
    bloco,
    unidade,
    status_cadastro,
    token_validacao,
    token_expira_em,
    tentativas_validacao
)

RELACIONAMENTOS:
- id_condominio referencia CONDOMINIOS(id).
- id_bloco referencia BLOCOS(id).


============================================================
2. CONDOMÍNIOS (CONDOMINIOS)
============================================================

CONDOMINIOS (
    id (PK),
    nome,
    numero_moradores,
    sindico_responsavel
)

OBSERVAÇÃO:
O atributo sindico_responsavel armazena a identificação do síndico
responsável pelo condomínio. No banco de dados atual, esse campo
não possui uma restrição FOREIGN KEY declarada.

7. RESERVAS DE CHURRASQUEIRA (RESERVAS_CHURRASQUEIRA)
============================================================

    id_condominio,

    horario_fim,

11. NOTIFICAÇÕES (NOTIFICACOES)
============================================================

NOTIFICACOES (
    id (PK),
    titulo,
    mensagem,
    tipo,
    escopo,
    condominio_id (FK),
    criado_por (FK),
    criado_em
)

RELACIONAMENTOS:
- condominio_id referencia CONDOMINIOS(id).
- criado_por referencia USUARIOS(id).

OBSERVAÇÃO:
O atributo condominio_id pode ser nulo, permitindo notificações
sem vínculo com um condomínio específico.

O atributo criado_por identifica o usuário responsável pela criação
da notificação e também pode ser nulo.


============================================================
12. DESTINATÁRIOS DE NOTIFICAÇÕES
    (NOTIFICACAO_DESTINATARIOS)
============================================================

NOTIFICACAO_DESTINATARIOS (
    notificacao_id (PK, FK),
    usuario_id (PK, FK),
    lida_em
)

RELACIONAMENTOS:
- notificacao_id referencia NOTIFICACOES(id).
- usuario_id referencia USUARIOS(id).

OBSERVAÇÃO:
A tabela NOTIFICACAO_DESTINATARIOS possui uma chave primária
composta pelos atributos notificacao_id e usuario_id.

Essa tabela associativa implementa o relacionamento N:M entre
USUARIOS e NOTIFICACOES, permitindo que uma notificação seja
enviada para vários usuários e que um usuário receba várias
notificações.

O atributo lida_em registra a data e o horário em que o usuário
visualizou a notificação. Caso ainda não tenha sido lida,
o valor permanece NULL.

14. RESUMO DAS CHAVES ESTRANGEIRAS (FK)
============================================================

USUARIOS:
- id_condominio -> CONDOMINIOS(id)
- id_bloco -> BLOCOS(id)

BLOCOS:
- id_condominio -> CONDOMINIOS(id)

GESTORES_CONDOMINIOS:
- usuario_id -> USUARIOS(id)
- condominio_id -> CONDOMINIOS(id)
- bloco_id -> BLOCOS(id)

PEDIDOS_SINDICO:
- usuario_id -> USUARIOS(id)
- condominio_id -> CONDOMINIOS(id)

BOLETOS:
- id_condominio -> CONDOMINIOS(id)
- id_usuario -> USUARIOS(id)

NOTIFICACOES:
- condominio_id -> CONDOMINIOS(id)
- criado_por -> USUARIOS(id)

NOTIFICACAO_DESTINATARIOS:
- notificacao_id -> NOTIFICACOES(id)
- usuario_id -> USUARIOS(id)

OBSERVAÇÃO:
As tabelas RESERVAS_CHURRASQUEIRA, RESERVAS_SALAO e REUNIOES
possuem atributos que identificam usuários ou condomínios,
mas esses atributos não foram definidos como chaves estrangeiras
no banco de dados atual.

O atributo sindico_responsavel da tabela CONDOMINIOS também
não possui uma restrição FOREIGN KEY declarada.

8. CONDOMINIOS — PEDIDOS_SINDICO: 1:N

9. CONDOMINIOS — BOLETOS: 1:N

10. USUARIOS — BOLETOS: 1:N

11. CONDOMINIOS — NOTIFICACOES: 1:N

12. USUARIOS — NOTIFICACOES (AUTOR): 1:N

13. NOTIFICACOES — NOTIFICACAO_DESTINATARIOS: 1:N

14. USUARIOS — NOTIFICACAO_DESTINATARIOS: 1:N

15. USUARIOS — NOTIFICACOES (DESTINATÁRIO): N:M


============================================================
16. OBSERVAÇÕES SOBRE A ESTRUTURA DO BANCO DE DADOS
============================================================

1. A tabela NOTIFICACAO_DESTINATARIOS implementa o relacionamento
   muitos-para-muitos (N:M) entre usuários e notificações.

2. A tabela BOLETOS possui relacionamentos com CONDOMINIOS
   e USUARIOS por meio de chaves estrangeiras.

3. As tabelas RESERVAS_CHURRASQUEIRA e RESERVAS_SALAO
   armazenam informações de reservas de espaços comuns.

4. A tabela REUNIOES armazena informações sobre reuniões
   vinculadas a condomínios.

5. As tabelas de reservas e reuniões possuem campos de
   identificação de usuários ou condomínios, mas não possuem
   FOREIGN KEY declarada no banco de dados atual.

6. A tabela CONDOMINIOS possui o atributo sindico_responsavel,
   mas não existe uma FOREIGN KEY declarada para esse campo.

7. As tabelas MENSAGENS e NOTIFICACOES possuem finalidades
   distintas. MENSAGENS armazena textos simples, enquanto
   NOTIFICACOES gerencia avisos e comunicados destinados
   aos usuários.

8. O modelo relacional contempla 12 tabelas, organizadas para
   atender às funcionalidades de gerenciamento de condomínios,
   usuários, reservas, reuniões, boletos e notificações.
